# OpenAI Cookbook adoption for Trade-Bot

## Scope and decision

Reviewed the official [OpenAI Cookbook](https://github.com/openai/openai-cookbook) repository on 13 October 2026. Its README describes examples and guides for OpenAI APIs, mainly in Python. The Cookbook is a reference library, not a runtime framework that should be copied wholesale into every application.

**Decision:** adopt the Cookbook's reusable engineering patterns, encode Trade-Bot-specific workflows as project skills, and keep a traceable map to upstream examples. Do not vendor the whole Cookbook. It contains unrelated domains, notebooks, external datasets/dependencies, deployment-specific examples, and recipes that are archived or use older API surfaces. Wholesale import would increase review, dependency, privacy, and maintenance burden without improving the deterministic trading core.

## What is being integrated now

The repository gains project-specific skills for engineering implementation, root-cause debugging, code review/PR handling, OpenAI SDK boundaries, evaluation/optimization, and parallel agent/sub-agent coordination. The existing evidence-first and delivery skills are aligned with the mandatory GitHub-only validation policy. The local engineering plugin packages the skills, includes an official Codex plugin manifest, and keeps the OpenAI documentation MCP read-only. A CI test guards that the plugin package and project-local skills remain in sync.

The repository already has compatible foundations: `AGENTS.md`/`CLAUDE.md` instructions, structured project skills, local Codex configuration, decision tracing and diagnostics, deterministic evaluation/tuning paths, quality/security registries, and a SHA-bound CI-notice preparation tool. This adoption extends those foundations rather than replacing them with a parallel agent framework.

## Deliberate non-integrations

- **No Cookbook wholesale import.** Notebook content and example-specific requirements do not belong in the application runtime.
- **No new mandatory OpenAI runtime dependency.** No concrete user-facing LLM feature was specified. A cloud model in the trade-decision loop would add cost, latency, network, data-egress, credential, availability, and tool-permission risks without a demonstrated benefit.
- **No agent-authorized trading side effects.** Any future research or operator-assistance agent remains advisory by default; deterministic code and existing risk/approval controls own trade authorization, sizing, and order execution.
- **No automatic prompt/model self-optimization in production.** Changes require frozen evaluation data, candidate-versus-baseline results, regression coverage, and explicit promotion gates.
- **No outdated SDK signature copying.** Archived Cookbook recipes are conceptual references only; current API/SDK docs and compatibility tests define implementation contracts.

## Rules for future SDK additions

Before introducing `openai`, `openai-agents`, or another agent/software SDK, document the feature owner and user benefit, optional-dependency decision, data sent to the provider, authentication and secret handling, network/timeout/retry budgets, rate-limit/cost ceilings, structured result schema, tool permission boundary, telemetry/redaction policy, offline fake-based tests, evaluation dataset, fallback/disable behavior, and duplicate-side-effect risk. No API key belongs in source code, plugin manifests, prompts, or repository configuration.
